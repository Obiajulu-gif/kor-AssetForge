# Backend deployment configuration

Use Go 1.25 or newer and a PostgreSQL database. From the repository root,
copy `backend/.env.example` to `backend/.env` and fill in the database and
network settings. Never commit the populated file.

## Required signing secret

Generate a new value with `./scripts/generate_jwt_secret.sh`, then set it as
`JWT_SECRET` through your secret manager or local environment file. The helper
requires OpenSSL and prints 32 random bytes encoded as 64 hexadecimal characters.
Missing, blank, or shorter-than-32-character values stop startup before database
connections or background jobs begin. Weak-looking values produce a warning.
See [Security](SECURITY.md) for rotation and storage guidance.

## Asset-token contract

Deploy and initialize the asset-token contract on the intended Stellar network
using the Stellar CLI and the contract's current initialization arguments.
The deployment orchestration is in `scripts/deploy_contracts.sh` and
`scripts/deploy_config.json`; review those arguments against the current contract
before deployment. The script records addresses in `backend/.contracts` and
`backend/.env.contracts`, with the asset-token entry named `ASSETTOKEN_CONTRACT_ID`.

Set `SOROBAN_ASSET_TOKEN_CONTRACT_ID` to the actual deployed asset-token address
in `backend/.env` or the process environment. Copy the address from the deployment
output; legacy `ASSET_CONTRACT_ID`, `ASSETTOKEN_CONTRACT_ID`, and `CONTRACT_ID`
variables do not substitute for this required setting. Generated contract files
are not automatically loaded by the backend.

The address must be a canonical uppercase Stellar contract StrKey: 56 characters,
starting with `C`, containing a 32-byte contract hash and a valid checksum.
An account address starting with `G`, a placeholder, a malformed value, or an
absent value stops startup. The SDK validates the type and checksum; a length or
prefix check alone is insufficient. Format validation does not verify deployment,
initialization, or that the contract exists on your selected network.

Both `backend/main.go` and `router.SetupRouter` validate these settings. HTTP
and WebSocket authentication use the same validated signing secret; asset
tokenization passes the configured contract address to the Stellar client.

The existing `StellarClient.InvokeContract` implementation remains a stub that
returns `not implemented`. This configuration change does not complete Soroban
RPC submission. Tokenization still returns HTTP 202 when its database record was
created but the contract invocation failed; deployment readiness requires the RPC
integration to be completed and tested separately.

## Running

For a direct backend process, run `go run .` from `backend/`, where `.env` is
loaded. For local Docker Compose, supply the same values through the host
environment or `docker compose --env-file backend/.env up -d`; Compose passes
`JWT_SECRET` and `SOROBAN_ASSET_TOKEN_CONTRACT_ID` to the backend container.

For production Compose, set `SOROBAN_ASSET_TOKEN_CONTRACT_ID` in `.env.prod`.
The JWT secret remains in `secrets/jwt_secret.txt`, generated by
`scripts/generate_secrets.sh` and exported by the backend container's entrypoint.
See [Docker deployment](DOCKER_DEPLOYMENT.md) for the production stack.
